# Лабораторна робота №4. Клієнтський застосунок та презентація архітектурних рішень

**Тема:** Клієнтський застосунок та презентація архітектурних рішень
**Мета:** Створити клієнтський застосунок з графічним інтерфейсом, який взаємодіє виключно через API Gateway (`http://localhost:5000`), демонструє коректну обробку всіх помилок (401, 429, таймаутів, деградації), запобігає дублюванню дій, та захистити виконані архітектурні рішення перед аудиторією.

---

## 1. Головні правила та обмеження клієнта

1. **Консольний застосунок заборонено:** Потрібен інтерфейс з екранами та станами (Blazor WebAssembly / Server, React, Vue, HTML+JS, WPF, Avalonia, MAUI або Telegram-бот).
2. **Єдина адреса:** Клієнт взаємодіє **лише зі шлюзом** (`http://localhost:5000`). Адрес окремих сервісів (`:5001`, `:5002`, `:5003`, `:5193`) у коді клієнта бути не повинно взагалі.
3. **Жодної бізнес-логіки на клієнті:** Клієнт показує отримані дані, не рахує самостійно знижки, фінальні вартості оренди чи доступність трактора.
4. **Жодних секретів у клієнті:** Усі API-ключі та секретні паролі не потрапляють у клієнтський код.
5. **Ідентифікатор користувача клієнт не надсилає:** Сервер і шлюз беруть `userId` виключно з JWT-токена.

---

## 2. П'ять обов'язкових екранів

| № | Екран | Що має містити |
|---|---|---|
| 1 | **Вхід (Login)** | Форма входу (Email/Пароль), відображення помилки при некоректних даних (`401`), збереження пары токенів у сховищі. |
| 2 | **Список об'єктів каталогу** | Перелік сільгосптехніки та товарів, пошук (debounce 300-500мс), фільтрація за категорією, пагінація (`page`, `pageSize`). |
| 3 | **Деталі об'єкта** | Дані про техніку + активна оренда користувача **через 1 складений запит ЛР3** (`GET /api/v1/gateway/catalog-items/{id}/details`). Жодних трьох окремих викликів! |
| 4 | **Створення операції (Оренда)** | Форма бронювання техніки (дати, адреса доставки поля), клієнтська та серверна валідація, індивідуальні помилки під кожним полем, генерація `Idempotency-Key`, блокування кнопки від подвійного кліку. |
| 5 | **Мої операції** | Список орендованої техніки поточного користувача зі статусами (`Confirmed`, `Pending`, `Cancelled`) та можливістю скасування операції. |

---

## 3. Чотири стани кожного екрана

Кожен екран повинен явно відображати 4 стани (а не просто порожній екран або вічний спінер):
1. **Завантаження:** Індикатор завантаження або скелетон (skeleton UI), кнопки взаємодії заблоковані (`disabled`).
2. **Успіх:** Отримані дані відображаються користувачеві.
3. **Порожньо:** Повідомлення на кшталт «Нічого не знайдено за вашим запитом» або «У вас ще немає оформлених оренд». Це нормальний стан, а не помилка!
4. **Помилка з можливістю повтору:** Чітке, зрозуміле для людини повідомлення (без назв C# класів чи stack trace) та кнопка **«Повторити спробу»**.

---

## 4. Обов'язкове опрацювання критичних ситуацій

### 4.1. Централізований шар API (`AuthHandler`)
Усі запити виконуються через централізований клієнт (наприклад, `DelegatingHandler` у C# Blazor або `axios interceptor` у JS):
- Токен `Bearer <JWT>` підставляється автоматично.
- **Обробка `401 Unauthorized`:** ОДНА спроба оновити токен за допомогою збереженого `refresh_token` (`POST /api/v1/auth/refresh`). У разі успіху — автоматичний повтор початкового запиту. Якщо оновити не вдалося — очищення сховища та перенаправлення на екран входу.
- **Обробка `429 Too Many Requests`:** Зчитування заголовка `Retry-After`. Показ повідомлення користувачеві: «Забагато запитів. Зачекайте X секунд». Кнопка блокується на час таймауту; запити повторно в цей час не надсилаються!
- **Часткова деградація (з ЛР3):** Якщо складений ендпоінт повернув дані трактора, але повідомив про недоступність операційного сервісу — відобразити техніку та плашку «Інформація про ваші оренди тимчасово недоступна», але не показувати хибне враження, ніби оренди немає.
- **Таймаут або недоступність сервера:** Зрозуміле людині сповіщення та кнопка «Спробувати знову».

### 4.2. Створення без дублів (`Idempotency-Key`)
- Клієнт генерує `UUID v4` на кожну спробу користувача.
- При натисканні кнопки «Оформити оренду» кнопка негайно блокується (`disabled`), щоб захистити від подвійного кліку.
- Якщо сталася мережева помилка та користувач натискає «Повторити спробу», клієнт надсилає той самий `Idempotency-Key`. Сервер не створює друге замовлення, а повертає вже створений результат.

### 4.3. Оптимізація пошуку (Debounce)
- Введення тексту в поле пошуку не повинно спамити запитами на кожну літеру.
- Затримка (debounce) 300–500 мс перед відправкою запиту на сервер.

---

## 5. Презентація архітектурних рішень (7–10 хв)

Презентація містить 5–8 слайдів:
1. **Слайд 1. Предметна область:** Аграрна платформа `AgriculturalWebsite` — оренда сільгосптехніки та продаж продукції фермерам.
2. **Слайд 2. Архітектурна схема:** Gateway (`:5000`), AuthService (`:5001`), CatalogService (`:5002`), OperationsService (`:5003`), Моноліт (`:5193`), бази даних, взаємодія через REST та gRPC.
3. **Слайд 3. Декомпозиція моноліту (ADR):** Чому спочатку винесли Auth і Catalog (найменша зв'язність, чіткі межі), потім Operations (замовлення/оренда над каталогом).
4. **Слайд 4. Найважче рішення та альтернативи:** Вибір способу комунікації (gRPC з дедлайнами проти HTTP), перенесення валідації токена на шлюз, стратегія обробки розривів та деградації.
5. **Слайд 5. Що працює ідеально, а що має обмеження (чесний підсумок):** Що реалізовано (кеш, rate limit, складений запит), які компроміси виникли (затримка мережі, відсутність distributed transactions).
6. **Жива демонстрація:** Вхід -> Перегляд списку -> Складений екран деталей -> Оформлення оренди з Idempotency -> Мої оренди -> Імітація падіння сервісу / 429.
