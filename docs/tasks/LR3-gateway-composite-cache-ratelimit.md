# Лабораторна робота №3. Розширення API Gateway

**Тема:** Розширення API Gateway: складений запит, автентифікація, кеш, обмеження частоти
**Мета:** Перетворити шлюз із простого маршрутизатора на повноцінні «вхідні двері системи» (Smart Gateway / BFF): збирати один складений екран клієнта паралельно з кількох сервісів, кешувати загальні довідкові дані, обмежувати частоту запитів, перенести перевірку токена на шлюз та ізолювати порти внутрішніх сервісів.

---

## 1. Головне правило та заборони
> **Правило:** Шлюз — єдині вхідні двері. Клієнт звертається ТІЛЬКИ на порт шлюзу (`5000`).
> **Жодної бізнес-логіки у шлюзі:** Шлюз складає, кешує, обмежує частоту й перевіряє токен, але **не вирішує**, чи можна орендувати трактор, скільки коштує знижка та чи достатньо коштів на рахунку. Це обов'язок мікросервісів!

---

## 2. Складений (агрегований) ендпоінт

Для аграрного сайту типовий екран — **«Деталі техніки з моєю активною орендою»**:
- **Маршрут на шлюзі:** `GET /api/v1/gateway/catalog-items/{id}/details`
- **Виклики виконуються паралельно:**
  ```csharp
  var itemTask = _catalogClient.GetItemAsync(id, ct);
  var activeRentalTask = _operationsClient.GetMyActiveRentalAsync(userId, id, ct);

  await Task.WhenAll(itemTask, activeRentalTask);
  ```
- **Власний DTO шлюзу:** Формат належить шлюзу (а не сліпе склеювання):
  ```json
  {
    "item": {
      "id": 15,
      "title": "Трактор John Deere 8R",
      "pricePerDay": 8500.00,
      "category": "Важка техніка"
    },
    "myActiveOperation": {
      "rentalId": 104,
      "status": "Confirmed",
      "startDate": "2026-11-05T08:00:00Z",
      "endDate": "2026-11-10T18:00:00Z"
    },
    "operationsServiceAvailable": true
  }
  ```

### 2.1. Таймаути та часткова деградація
- На всі виклики зі шлюзу до сервісів встановлюється таймаут (2 секунди):
  ```csharp
  builder.Services.AddHttpClient<CatalogClient>(c => {
      c.BaseAddress = new Uri(cfg["Services:Catalog"]!);
      c.Timeout = TimeSpan.FromSeconds(2);
  });
  ```
- **Часткова деградація:** Якщо `CatalogService` недоступний — повертається помилка на весь запит (`502/503`), бо без товару екран беззмістовний. Якщо недоступний `OperationsService` — повертаються дані техніки, а секція оренди позначається явно як недоступна (`"operationsServiceAvailable": false`), але НЕ підміняється на `null` без позначки!
  *(Інакше клієнт подумає, що активної оренди немає, і оформить другу оренду).*

## 3. Автентифікація на шлюзі та безпека сервісів

1. **Токен перевіряється один раз — на шлюзі:**
   - Шлюз валідує JWT за допомогою `AddJwtBearer()`.
   - З claims витягуються `userId` та `roles`.
   - Шлюз передає внутрішнім сервісам заголовки:
     - `X-User-Id: <userId>`
     - `X-User-Roles: <roles>`
2. **Захист внутрішніх сервісів:**
   - Внутрішні сервіси прив'язуються виключно до локального інтерфейсу (`127.0.0.1:5001`, `127.0.0.1:5002`, `127.0.0.1:5003`) або закриваються мережею Docker.
   - Спроба клієнта напряму звернутися до сервісу в обхід шлюзу повинна відхилятися!
   - **Увага:** `userId` завжди береться з токена шлюзом, а не з тіла/query запиту клієнта.

---

## 4. Локальний кеш у пам'яті (`IMemoryCache`)

1. **Що кешуємо:**
   - Спільні дані для всіх: каталог техніки (`/api/v1/catalog/items`), категорії, довідники.
   - **TTL:** 60 секунд (для каталогу) або 300 секунд (для довідників категорій).
2. **Що категорично ЗАБОРОНЕНО кешувати:**
   - Персональні дані: історію оренди, профіль користувача, кошик, баланс.
   - *(Кешування персональних даних — це штраф -2 бали як критична вразливість безпеки).*
3. **Ключ кешу:**
   - Складається з роуту, `itemId`, параметрів сторінки та фільтрів: `$"catalog_item_{id}"`, `$"catalog_list_p{page}_s{pageSize}_cat{catId}"`.
4. **Інвалідизація:**
   - Якщо шлюз пропускає запит створення, редагування або видалення (`POST / PUT / DELETE` на `/api/v1/catalog/items/{id}`) і отримує успішний статус (`200 / 201 / 204`) — шлюз негайно видаляє відповідний ключ із кешу (`_memoryCache.Remove($"catalog_item_{id}")`).

---

## 5. Обмеження частоти запитів (Rate Limiting)

Використовується `Microsoft.AspNetCore.RateLimiting` в ASP.NET Core:
1. **Розподіл за суб'єктом:**
   - Для **авторизованих користувачів:** ліміт прив'язується до `UserId` (наприклад, 100 запитів на хвилину).
   - Для **анонімних користувачів:** ліміт прив'язується до `IP-адреси` (наприклад, 20 запитів на хвилину).
   - *Чому так:* за однією корпоративною NAT/IP може бути сотня легітимних співробітників, тому авторизованих не можна карати загальним лімітом однієї IP-адреси.
2. **Окремий жорсткий ліміт на ендпоінт входу (`POST /api/v1/auth/login`):**
   - Не більше 5 спроб на хвилину на одну IP-адресу для захисту від підбору паролів (brute-force).
3. **Відповідь при перевищенні:**
   - HTTP статус: `429 Too Many Requests`.
   - Заголовок: `Retry-After: <секунди>`.
   - Тіло відповіді: у стандартному форматі `ProblemDetails` (RFC 9457).

---

## 6. Єдиний формат помилок ProblemDetails
Всі помилки шлюзу (401, 403, 404, 429, 502, 503, 504) повертаються у стандартному форматі:
```json
{
  "type": "https://httpstatuses.com/429",
  "title": "Too Many Requests",
  "status": 429,
  "detail": "Ліміт запитів вичерпано. Спробуйте через 15 секунд.",
  "instance": "/api/v1/gateway/catalog-items/15/details"
}
```

---

## 7. Інтеграційні тести шлюзу (мінімум 5 обов'язкових)

1. **Складений ендпоінт (усі сервіси доступні):** Повна відповідь, присутні дані техніки та оренда.
2. **Один сервіс недоступний (стаб кидає помилку/таймаут):** Свідома часткова відповідь, клієнт чітко бачить ознаку відсутності зв'язку.
3. **Запит без токена:** `401 Unauthorized` у форматі `ProblemDetails`, у внутрішні сервіси жодного виклику не надсилається.
4. **Перевищення ліміту запитів:** Повертається `429 Too Many Requests` із валідним заголовком `Retry-After`.
5. **Повторний запит тих самих спільних даних:** Відповідь повертається з кешу, повторного мережевого виклику до `CatalogService` немає.
6. **Два різні користувачі звертаються за тим самим маршрутом:** Кожен отримує власні дані (перевірка відсутності кешування персональних даних).
