# ADR-0002. Ocelot як шлюз перед монолітом

## Статус
Accepted

## Контекст
`AgriculturalWebsite` має вебсторінки та API. Поточний HTTP-профіль моноліту налаштований на `http://localhost:5193`. ЛР0 вимагає єдину зовнішню точку входу `http://localhost:5000`, з якої запити передаються далі без зміни бізнес-логіки моноліту. У наступних роботах частину маршрутів планується спрямувати на окремі сервіси.

## Розглянуті варіанти
1. **Без шлюзу.** Просто, але клієнт мусить знати адресу кожного застосунку; винесення сервісу змінює клієнтську конфігурацію.
2. **Ocelot.** Маршрути описуються JSON-конфігурацією, підходить до ASP.NET Core і дозволяє змінити downstream для окремої групи маршрутів.
3. **YARP.** Потужний reverse proxy для .NET, але маршрути та додаткові можливості зручніше налаштовувати кодом; для цієї лабораторної потрібна мінімальна конфігураційна реалізація.
4. **Керований хмарний шлюз.** Має більше інфраструктурних можливостей, але зайвий для локального навчального проєкту.

## Рішення
Використати Ocelot як окремий ASP.NET Core-проєкт `ApiGateway` на порту `5000`. Явні маршрути для наявних API-груп `/api/auth/{everything}` і `/api/products/{everything}` (а також `/api/tractors/{everything}` та `/api/trailers/{everything}`) розташовуються перед `/api/{everything}`. У ЛР0 усі вони ведуть до моноліту. Цільові версійовані маршрути наступної ЛР — `/api/v1/auth/**`, `/api/v1/users/**` і `/api/v1/catalog/**`; вони будуть перемкнуті на AuthService `:5001` та CatalogService `:5002` під час виконання ЛР1. Окремий catch-all для решти шляхів підтримує вебсторінки та інші ресурси.

## Наслідки
- Позитивні: клієнт має одну адресу; маршрути можна перемикати конфігурацією; шлюз може централізовано додавати correlation ID і журналювати запити.
- Негативні: з’являється ще один процес і мережевий перехід; шлюз стає точкою відмови та потребує перевірки доступності.
- Шлюз не реалізує бізнес-логіку й не звертається до бази даних. Моноліт зберігається окремим проєктом без зміни його вихідних файлів.
