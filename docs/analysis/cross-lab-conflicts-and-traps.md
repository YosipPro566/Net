# Аналіз помилок, архітектурних колізій та підводних каменів за методичками ЛР0 — ЛР4

У цьому документі проведено ретельний аудит вимог усіх п'яти методичок (ЛР0, ЛР1, ЛР2, ЛР3, ЛР4) стосовно проєкту **`AgriculturalWebsite`**, виявлено приховані конфлікти між роботами, небезпечні пастки та розписано систему штрафів викладачів.

---

## 1. Архітектурні конфлікти та еволюція вимог між роботами

### 1.1. Конфлікт реалізації API Gateway: Ocelot (ЛР0) проти Smart Gateway (ЛР3)
* **Що вимагає ЛР0:** Використовувати бібліотеку Ocelot (`UseOcelot()`). У методичці ЛР0 окремо зазначено:
  > *«UseOcelot() — термінальний обробник: усе, що йде після нього, вже не виконається. Тому не додавайте у шлюз app.MapGet(...) та інші мінімальні API — вони не спрацюють.»*
* **Що вимагає ЛР3:** Шлюз повинен мати:
  1. Власний ендпоінт складеного запиту (`GET /api/v1/gateway/.../details`), де виконується C# код з `Task.WhenAll`.
  2. Кешування через `IMemoryCache` з інвалідизацією.
  3. `builder.Services.AddRateLimiter(...)` із розбиттям по `UserId` та `IP`.
  4. Перевірку токена та прокидання `X-User-Id`.
* **У чому пастка і помилка студентів:**
  В Ocelot агрегація через `Aggregators` в `ocelot.json` є вкрай незручною, обмеженою і не дозволяє реалізувати повноцінну логіку таймаутів, часткової деградації, DTO екрана та кастомного інвалідування кешу.
* **Правильне інженерне вирішення:**
  Усі кастомні ендпоінти шлюзу (складений запит, `/health`, rate limiter middleware, jwt auth) реєструються в ASP.NET Core конвеєрі **ДО** виклику `await app.UseOcelot()`. Усі запити, які не збіглися з кастомними маршрутами, передаються далі по конвеєру в Ocelot (або на етапі ЛР3 Ocelot замінюється/доповнюється YARP / Minimal API контролерами шлюзу).

### 1.2. Кардинальна зміна моделі перевірки токенів (ЛР1/ЛР2 проти ЛР3)
* **У ЛР1 та ЛР2:** Авторизація **децентралізована**. Токен генерує `AuthService`, а `CatalogService` та `OperationsService` перевіряють його **самостійно** через спільний секрет `Jwt:Key` (`AddJwtBearer`). Клієнт передає заголовок `Authorization: Bearer <JWT>`, і шлюз просто транслює його далі.
* **У ЛР3:** Автентифікація переноситься **на шлюз**. Токен перевіряється один раз на вході шлюзом. Шлюз витягує `sub` (UserId) та `roles` і передає сервісам HTTP-заголовки:
  `X-User-Id: {userId}` та `X-User-Roles: {roles}`.
* **Критична вразливість (штраф -1.5 бала):**
  Якщо сервіси починають довіряти заголовку `X-User-Id`, але їхні порти (`:5001`, `:5002`, `:5003`) залишаються відкритими назовні (`0.0.0.0`), будь-який зловмисник може надіслати запит напряму в сервіс із заголовком `X-User-Id: admin` і отримати повний доступ!
* **Вимога для ЛР3:** Сервіси повинні слухати виключно локальний інтерфейс `127.0.0.1` або знаходитися у внутрішній закритій мережі Docker Compose.

### 1.3. Вибір операційного сервісу для AgriculturalWebsite (ЛР2)
* **Проблема моноліту:** У моноліті `AgriculturalWebsite` є моделі каталогу (`Product`, `Tractor`, `Trailer`), сутності `Account/Identity`, а також `Chat` та `Favorite`. Сутності оренди або замовлень не було оформлено як окремий бізнес-процес.
* **Чому `Favorite` не підходить як операційний сервіс:**
  Методичка ЛР2 чітко зазначає: операційний сервіс повинен змінювати стан системи (створення, зміна, скасування), мати власний набір таблиць і звертатися до каталогу з перевіркою параметрів. Обране (`Favorite`) є пасивною міткою і не містить розрахунку дат, ціни, статусів та ідемпотентності.
* **Вирішення:** Для аграрної платформи створюється повноцінний **`AgriRentalService` (або `OrderingService`)**:
  - Відповідає за оренду сільгосптехніки (тракторів, причепів) або гуртове замовлення зерна.
  - Має статуси (`Pending`, `Confirmed`, `Cancelled`).
  - Виконує виклик до `CatalogService` через gRPC з дедлайном.

### 1.4. Пастка «пливучих цін» (ItemSnapshot) у ЛР2
* **Типова помилка:** У таблиці оренди/замовлення зберігають тільки `ItemId` (ID трактора).
* **Наслідок:** Якщо через місяць адміністратор у `CatalogService` змінює тариф оренди трактора з 5000 грн на 9000 грн, у всіх старих замовленнях користувачів суми в історії та звітах автоматично зміняться на 9000 грн!
* **Вимога ЛР2:** Зберігати денормалізований знімок даних (`ItemTitleSnapshot`, `ItemPriceSnapshot`) безпосередньо в записі операції.

---

### 1.5. Пастка часткової деградації складеного ендпоінта (ЛР3 / ЛР4)
* **Типова помилка:** Якщо `OperationsService` недоступний або впав за таймаутом (2 сек), розробник повертає у відповіді `"myActiveOperation": null`.
* **Наслідок у клієнті (ЛР4):** Клієнт бачить `null`, думає, що оренди немає, і створює нову повторну оренду.
* **Вимога:** Клієнт і шлюз повинні чітко розрізняти:
  - *«Оренди немає»* (`operationsServiceAvailable: true`, `myActiveOperation: null`)
  - *«Сервіс оренди недоступний»* (`operationsServiceAvailable: false`, повідомлення «Неможливо завантажити статус вашої оренди, спробуйте пізніше»).

---

### 1.6. Вразливість кешування персональних даних (ЛР3)
* **Типова помилка (штраф -2 бали як вразливість):**
  Кешування відповіді складеного ендпоінта цілком або збереження списку оренди в загальному кеші за простим ключем.
* **Наслідок:** Користувач Б робить запит і бачить у відповіді оренду та персональні дані користувача А!
* **Вимога:** У кеш потрапляють **виключно спільні дані** (публічний каталог техніки, довідники). Персональні дані не кешуються ніколи.

---

### 1.7. Дублювання операцій і клієнтський Idempotency-Key (ЛР2 / ЛР4)
* **Помилка:** Генерувати `Idempotency-Key` на сервері.
* **Чому це безглуздо:** Клієнт при збої мережі (таймауті) надсилає запит повторно. Якщо сервер генерує ключ сам, кожна спроба створить нову операцію і спише кошти вдруге.
* **Вимога:** Клієнт генерує один UUID на одну спробу користувача і надсилає його в заголовку `Idempotency-Key`. При повторній відправці через помилку зв'язку надсилається **той самий ключ**. Кнопка в інтерфейсі обов'язково блокується на час виконання запиту.

---

### 1.8. Порти: розбіжність навчальних прикладів та реального репозиторію
* У методичках для моноліту вказано порт `:5100`.
* У поточному проєкті `AgriculturalWebsite` у файлі `src/Monolith/Properties/launchSettings.json` порт задано як **`:5193`**.
* **Рішення:** Залишати `:5193` для моноліту або зафіксувати спільну домовленість, щоб не ламати наявні конфігурації. Порти для нових сервісів відповідають методичкам:
  - Gateway: `5000`
  - AuthService: `5001`
  - CatalogService: `5002` (gRPC `5102`)
  - OperationsService: `5003` (gRPC `5103`)

## 3. Рекомендації для отримання максимального балу (+3 бонусних бали)

1. **Docker Compose для всього стеку (бонус +3 бали в ЛР2, ЛР3, ЛР4):**
   - Написати `docker-compose.yml`, де однією командою `docker compose up --build` піднімаються всі сервіси, бази даних (MySQL / SQLite), Redis/шлюз та клієнтський застосунок.
2. **Єдиний Swagger на шлюзі (ЛР3):**
   - Шлюз агрегує OpenAPI документацію всіх внутрішніх мікросервісів у єдиний UI через ендпоінти Swagger/Scalar.
3. **Resilience з Polly (ЛР3 / ЛР2):**
   - Додати політики повторів (retry with exponential backoff) для тимчасових мережевих збоїв.
4. **Скелетони (Skeleton UI) та темна тема в клієнтському інтерфейсі (ЛР4):**
   - Під час завантаження відображати анімовані контури карток замість звичайного крутильного індикатора.
